* 通信流
- debugger(gdb) <-> openocd(translator) <-> jlink <->
- TAP controller <-> dtm(transport) <->
  1. TAP的IR寄存器至少5bits宽,意味着至少支持32个dtm的registers;
- dmi(apb bus) <-> dm
  1. dmi的地址总线宽度7~32 address bit宽,意味着支持2^7~2^32个dm 
- <->core hart: 通过abstract command或progbuf控制hart
- <->progbuf
- <->sysbus <-> 直接访问mem不经过hart;
* OpenOCD源码框架
OpenOCD的代码结构整体分成两大部分:
1. 对于输入的configure文件的解析.该文件用来配置JTAG通信中各个参数,甚至
   包括对目标板的一些初始化操作也在文件中预先定义好,比如对于FLASH以及
   RAM的一些初始化操作等.该文件的语法是TCL的一个子集,OpenOCD集成了一个
   C语言编写的TCL的解释器(Jim). OpenOCD在启动后会解析该TCL语法的
   configure文件,然后调用相应的预先注册好的command handler函数执行特定
   的命令(下文会涉及handler函数的注册).
2. OpenOCD是通过socket的方式和GDB进行通信的.在初始化阶段也包含了socket
   的建立.初始化完成后,就会进入server_loop()函数中,在这个函数的大循环
   中,接收来自GDB的命令(GDB命令的解析下文会涉及).对每个命令字串,调用相
   应的函数进行特定的处理.比如设置断点,单步运行等等. 通过一层层的call
   stack,最终将命令发送给MCU的Debug Module模块中. 当然在处理完成后会通
   过socket将response的消息反馈给GDB.

** OpenOCD访问Debug Module寄存器
这一部分涉及的内容是与处理器平台相关的,本文主要基于RISC-V平台,但是原理
都是相通的. 一般来讲所有的debug逻辑的处理都是基于对MCU内部寄存器的访问
来实现的.
1. OpenOCD对于RISC-V内部的CSR等寄存器的访问需要借助DTM寄存器来进行访问的.
  当需要访问JTAG寄存器的时候,需要使用如表[[tbl-dtmreg]]中Debug Module

限于篇幅的原因就不再贴调用流程图,简单描述如下:
- 首先OpenOCD需要构造一条汇编指令,该指令的作用是读取寄存器的内容到一个
  特定的MCU寄存器中,比如 csrr s0,mstatus. 该条指令的含义是将RISC-V的
  mstatus寄存器内容读取到s0寄存器中, 它是一个机器码,该机器码包含了源操
  作数和目的操作数.
- 将该机器码发送到Debug Module的bus寄存器progbufn(program buffer
  [n=0~15])中.
- 构造abstract command字段,将该字段发送到"Abstract Comand"寄存器中,触
  发存放在program buffer中的机器码被MCU core获取,从而得到执行,数据存放
  到了s0寄存器中.
- 构造abstract command字段,将该字段发送到"Abstract Comand"寄存器中,触
  发将s0寄存器中的数据拷贝到 "Abstract Data 0"寄存器中.
- OpenOCD直接读取 "Abstract Data 0"寄存器中的数据,从而获取最终需要的寄
  存器中的数据.
** JTAG物理信号的解析
上述所有对寄存器的访问都是通过JTAG的物理引脚来传递信号的.一般的JTAG物
理信号主要包含四个pin脚:
- TCK: 移位时钟引脚
- TMS: TAP (test access point) 的状态机切换信号引脚
- TDI: 数据移位输入
- TDO: 数据移位输出

** 小结
对于OpenOCD源码的分析到这里就基本结束了.其实最关键的部分还是需要对于特
定处理器的Debug Module中各个控制逻辑的熟悉程度.比如设置一个断点到CPU中,需
要设置哪些DM中的寄存器以及按照什么样的逻辑顺序来操作.这些都需要了然于
胸,才能写出健壮的,适配于特定处理器的OpenOCD.


但大部分情况下,我们只需要了解OpenOCD的基本工作原理即可.在了解的基础上,
当JTAG通信工作不正常时可以定位到问题的原因就可以了.在这里扩展的谈谈GDB
与OpenOCD以及Debug-Module之间的互动关系: 在OpenOCD建立起了GDB与
DebugModule之间的通信链路以后,在调试的时候,需要使用GDB将所要调试的ELF
文件进行加载,GDB的加载过程其实分两个主要部分,一个是将ELF文件中的符号表
信息进行提取,这些信息会保留在GDB内部,GDB后续进行单步调试就是依赖与这些
信息的.另一个是将去掉了符号表等信息剩下的binary通过已经建立好的链路下
载到CPU侧. 在开始进行调试的时候,由于GDB内部已经得到了所有符号的信息,代
码从哪个地址开始执行,每行代码所在的地址这些都是知道的.比如单步运行,GDB
只需要发送单步运行的命令即可，单步运行前的起始位置GDB是知道的，单步运
行只不过是运行到下一个位置而已；还比如设置断点到某行代码处，该行代码所
处的地址GDB根据所保留的符号信息是很清楚的，只需要将要设置的断点处的地
址发送给OpenOCD即可，OpenOCD就会将后续的事情处理完毕；OpenOCD其实在整
个过程中除了建立链路外，还起到了一个转译命令的作用，将通信链路两端发送
来的数据通过转译再传递出去.

** FLASH刷写准备
在开始将image文件中的数据刷写到flash上之前,OpenOCD自己需要完成一个重要
的工作,那就是编译出一个可以运行在目标处理器上的小程序,这个小程序很简单,主
要的逻辑就是操作处理器中关于SPI的一组寄存器,将来自OpenOCD的image数据通
过SPI总线写入到FLASH中. 对于RISC-V平台来讲,目前它是放在这个路径下
的:"riscv-openocd/contrib/loaders/flash/fespi/",它最终会生成两个版本的
binary文件: riscv32_fespi.inc与riscv64_fespi.inc分别对应32位与64位的版
本.这两个bin文件可以在编译OpenOCD工具的时候自动生成,也可以在该目录下手
动编译生成. 打开它里面的Makefile文件,很多的疑问迎刃而解:首先它使用了
"-fPIC"的编译选项,保证了生成出来的代码是与地址无关的,那么不管这个代码
下载到哪个地址边界处,它都是可以正常运行的. 其次它使用了"-Obinary"的选
项,将ELF文件不需要的垃圾信息都清除掉,只留下最小最干净的binary. 最后它
使用了 "-nostdlib"以及"-nostartfiles",因此它自己写了一个很小的入口汇编
文件"riscv_wrapper.S"作为替代.


这样一个干净小巧的可运行在RISC-V平台上代码就完成了.再多说几句关于这个运
行在处理器上的小程序的处理逻辑. 打开它的文件"riscv_wrapper.S"如下图所
示, 因为代码很短我就直接全部贴出来并加以说明: 首先stack的空间它是已经
开辟好了,在程序的入口首先设置好了栈寄存器sp的值,为以后进行函数调用做准
备;在下面截图的第15行进行了函数调用,进入到函数flash_fespi()中,这个函数
是这个片上小程序唯一的主体函数,刷写FLASH的工作就是在这里完成的.注意它
的入口参数有六个,一定要记住,后面我们会讲到. 在图[[img-flstart]]的第16行有
个ebreak指令,这个非常关键. 因为flash_fespi()函数不是个死循环,在完成
flash的刷写工作后,它会从该函数中返回(当然返回时,"a0"寄存器中带回了刷写

程序乱飞,此处ebreak指令的执行会将当前Core给Halt住,同时切换当前模式为
Debug模式,并等待OpenOCD的垂询.

在完成第一步的probe后, 就可以开始进行写flash的操作了,它的命令如下:

我们就分析 "flash write_bank" 这条命令,另一条命令多了erase的操作,写的
动作其实是一样的. 通过这条命令字串,OpenOCD可以很顺利的找到预注册的

#+caption: Flash Write Bank调用栈
#+name: img-fwbank
#+attr_latex: :placement [H] :width 0.6\textwidth
[[./pic/img-ooflashwbank.png]]


对于函数handle_flash_write_bank_command(),详细分析如下:
- 首先根据传递进来的bank_id通过查找flash_banks[]数组找到匹配项.
- 获取offset的值,该值是相对于bank的offset,未来作为一个目的地址使用的.
- 打开输入的image-file的句柄,并读取到本地新分配的buffer中
- 然后调用flash_driver_write()函数,开始将存放好的image-file中的数据写
  入到特定的flash-bank中.
  


对于flash_driver_write()->fespi_write()函数,详细分析如下:
- 校验flash要写入的bank中的每个sector是否被保护了,若是则无法继续写则返
  回
- 确定好后面要下载的片上运行小程序及其大小: riscv32_bin/riscv64_bin,
  就是预备知识里面讲到的程序
- 调用target_alloc_working_area()函数: 先在OpenOCD中开辟一个buffer,大
  小是要下载的bin的大小.建立相应的管理结构体. 调用函数
  target_read_memory()将Core上由target->working_area_phys指定的地址,由
  target->working_area_size指定大小的这块区域的数据读取到本地刚开辟的
  buffer中,备份起来.
- 调用target_write_buffer()函数,将小程序bin(SPI的驱动代码)写入到
  target->working_area_phys指定的起始地址处.如果写的过程中发生失败,那
  么调用target_free_working_area()函数将备份的数据恢复到Core中去.
- 调用target_get_working_area_avail()函数中,将最终要写入的image-file那
  么大的一块数据这样的空间对应的一个管理实例给开辟出来.
- 再次调用target_alloc_working_area()函数,这次开辟的数据区是为了要下载
  image-file中的数据到FLASH中而分配的,因为先由OpenOCD下载数据到Core的
  working-area中,最后才有片上小程序将working-area中存放的image-file中
  的数据写入到FLASH中去的. 所以Core中的working-area上的这块区间的数据
  也需要备份到OpenOCD的本地buffer中.
- 在调用target_write_buffer()函数写入image-file中的数据之前,首先需要配
  置片上小程序在运行时的那六个入参(这个在预备知识中已经提及).
- 这里就开始调用target_write_buffer()将image-file中的数据写入到Core中
  由configue文件中指定的working-area中了.
- 调用target_run_algorithm()函数,同时把预先配置好的含有六个入参的结构
  发送到Core中去,写入到Core中的a0~a5这六个寄存器中,作为片上小程序在
  "jal flash_fespi"时的入参. 这六个参数包含了SPI寄存器域的基地址,要访
  问的image-file临时存放的物理地址以及它的大小.
- 当片上小程序完成将image-file的数据由working-area通过SPI总线写入到
  FLASH这个过程后,就会从flash_fespi()函数返回后,就会执行"ebreak"指令而
  Halt住.
- 其实target_write_buffer()以及target_run_algorithm()函数都是多次被调
  用的, OpenOCD写入一部分数据到Core中的DDR中,就会触发片上小程序将这一
  部分数据搬移写入到FLASH中,这也是为了避免如果image文件过大,尝试在一次
  搬移中就完成的话,那么写入的时间就会过长,那样可能会出现问题,所以不得
  不切割成多次来处理.
- 在每次运行target_run_algorithm()函数时,OpenOCD都会持续的polling当前
  Debug-Module的状态,如果polling到的状态是"RISCV_HALT_BREAKPOINT",那么
  就表示当前的这次传输完毕了.就可以调整参数进行下一次的传输了. (其实这
  部分在<<RISCV上Semihosting功能浅析>>文章已经涉及到了)
- 完成所有的传输后,分别调用两次target_free_working_area()对备份到
  OpenOCD本地的两个数据区恢复到Core上对应的区间中去. 等于片上小程序以
  及image的缓存区的数据就被覆盖掉了.

** 小结
以上就是对OpenOCD所支持的FLASH烧写逻辑的分析. 可以看到它主要采用了下载
一个片上小程序到CPU上去的方式,由小程序来完成数据的搬移工作. OpenOCD先
将要烧写的image写入到CPU中由cfg文件指定的working-area中,然后由小程序通
过SPI总线写入到FLASH中,所有烧写工作完成后,擦除痕迹!

* OpenOCD复位
** SRST
SRST = System Reset，拉低后整机硬件复位；必须先在配置里声明 SRST 硬件
连接，才能手动 / 自动控制引脚电平。使用前必须，先声明 SRST 硬件模式。
- 常用配置
  + 选择复位信号类型
    #+begin_src tcl
      # 只接了SRST（最常用，SWD基本都用这个）
      reset_config srst_only
  
      # SRST + TRST 都接
      # reset_config trst_and_srst
  
      # 没接SRST，只能软件复位
      # reset_config none
    #+end_src
  + 电气驱动模式
    #+begin_src tcl
      # 绝大多数板子：上拉电阻，开漏输出（默认）
      reset_config srst_only srst_open_drain
  
      # 适配器直接推挽驱动，外部无上拉电阻才用
      # reset_config srst_only srst_push_pull
    #+end_src
  + 时序参数: 该设置可以防止复位不稳定
    #+begin_src tcl
      # SRST拉低保持时间（复位脉宽ms）
      adapter srst pulse_width 100
      # SRST释放后等待多久再通信（防抖）
      adapter srst delay 50
    #+end_src
  + 连接方式：常用于复位下连接烧录
    #+begin_src tcl
      # 先拉SRST再连接调试（解决锁死、读不出ID）
      reset_config srst_only srst_nogate connect_assert_srst
      # 默认：先释放SRST再连接
      # srst_nogate：SRST 拉低时依然可以走 JTAG/SWD 通信，必须搭配connect_assert_srst
      # reset_config srst_only connect_deassert_srst
    #+end_src
- 复位命令
  + 复位并立刻暂停 CPU：烧录必备
    #+begin_src tcl
      # 流程：拉低 SRST-> 延时释放->连接调试->CPU 停下
      reset halt
    #+end_src
  + 复位+初始化，不暂停。
    #+begin_src tcl
      reset init
    #+end_src
  + 复位后直接运行
    #+begin_src tcl
      reset run
    #+end_src
*** 控制SRST电平
底层手动控制SRST电平，可以比较精细的控制。
- 通用底层 JTAG 复位接口，所有适配器通用
  #+begin_src tcl
    # 参数：jtag_reset trst srst  1=拉低(assert) 0=释放(deassert)
    # 拉低SRST，保持复位
    jtag_reset 0 1
    sleep 200
    # 释放SRST，退出复位
    jtag_reset 0 0
  #+end_src
- FTDI 类适配器（FT2232/FT4232/DAPLink-FTDI）直接操作信号
  #+begin_src tcl
    # 拉低SRST（assert复位）
    ftdi set_signal nSRST 0
    sleep 100
    # 释放SRST
    ftdi set_signal nSRST 1
    # 高阻态
    # ftdi set_signal nSRST z
  #+end_src
- GPIO 适配器（sysfsgpio）
  #+begin_src tcl
    # 直接控制复位GPIO高低
    gpio set nSRST 0
    sleep 100
    gpio set nSRST 1
  #+end_src
*** 常用配置模板
以下为对于ARM/STM32类SWD，常用配置模板
#+begin_src tcl
  adapter speed 4000
  # SRST配置：开漏、复位可通信、复位下连接
  reset_config srst_only srst_open_drain srst_nogate connect_assert_srst
  adapter srst pulse_width 100
  adapter srst delay 50

  # 手动复位脚本示例
  proc hard_reset {} {
      jtag_reset 0 1
      sleep 150
      jtag_reset 0 0
      sleep 50
  }
#+end_src
